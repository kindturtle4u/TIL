# 4. 스펙결정을 위한 인터뷰

## 4.1 이론-요구사항인터뷰와 스펙결정
### 요구사항 엔지니어링
- 코드는 "어떻게" 의 영역
- 요구사항은 "무엇을"의 영역
- AI 시대 - 코드가 빠르게 쌓인다 -> 방향이 더 중요
- 기능 요구사항 - 시스템이 무엇을 해야 하는가
- 비기능 요구사항 - 어떤 조건을 만족해야 하는가

### AI 인터뷰 - 역할을 뒤집는다
- 개발자가 묻는 게 아니라 AI 가 묻게 한다 ( 질문해보렴 )
```shell
이 기능 정의서를 읽고 , 코드베이스를 탐색해서
구현 전에 확인이 필요한 것들을 질문해라.
한 번에 하나씩 질문하고 , 추천 방식도 포함해라.
```
- AI 는 수만 개 프로젝트의 실패 패턴을 학습 ( 나보다 낫다 ..)

### 3가지 프롬프트 패턴
- "한번에 하나씩" : 집중도 유지, 깊이있는 답변 유도
- "추천 방식도 이유와 함께": 판단 근거 제공, 결정 속도 향상
- "코드베이스 먼저 탐색": 현식적 질문, 기존 패턴과 충돌 방지

### spec-original vs spec-fixed
- `spec-original.md`: 원본 기능 정의서
- `spec-fixed.md`: 인터뷰 후 확정된 명세
- 추적성(Traceability): "왜 태그 최대 개수가 5개인가?"에 답할 수 있어야 한다. 변경 이유가 기록되어야 나중에 제약을 바꿔도 되는지 판단 가능

## 4.2 실습-요구사항인터뷰와 스펙결정
- `git branch -a`: 브랜치 확인
- `git checkout -b feature/tag-spec`: 브랜치 생성
- `vi spec-original.md`
```markdown
# 태그 기능 정의서

## 기능 개요
노트에 태그를 추가하고 관리할 수 있다

## 기능 요구사항
- 노트에 태그를 추가할 수 있다
- 노트에 추가된 태그를 삭제할 수 있다
- 태그 목록을 노트 상세 화면에서 확인할 수 있다

## 비고
- 태그는 문자열로 저장한다
- 중복 태그는 허용하지 않는다
```

```shell
@docs/feature/tag/spec-original.md 를 읽어서 개발할꺼야
하지만 그것은 기본적인 기능정의서야.

나에게 질문해.
기본 데이터 구조, UI패턴, 엣지케이스를 고려해서 질문해.

한 번에 하나씩 질문하고, 내가 답하면 질문으로 넘어가.

추천방식도 이유와 함께 질문에 포함해라

최소 5개 이상 질문해. 너가 스펙에 대한 이헤/설계단계에서 의문이 없도록.
``` 
```shell
나머지는 질문하지 말고, 임의로 결정하고
같은 디렉토리에 spec-fixed.md로 저장해줘
```
